# Formation contrôle niveau 3 (B3.1) : premiers pas avec ROS 2

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Ouvrir un ou plusieurs terminaux ROS 2 dans le conteneur de B3 avec le Makefile
- Expliquer ce qu'est ROS 2 et le modèle publish-subscribe (node, topic, message)
- Inspecter un système qui roule avec les commandes `ros2 node` et `ros2 topic`
- Créer un workspace colcon, un package Python (`ament_python`) et un package C++ (`ament_cmake`)
- Écrire un publisher et un subscriber en Python, et un publisher en C++
- Bâtir, sourcer et nettoyer un workspace avec colcon

Prérequis : B2 terminé (Docker utilisable sans `sudo`, Compose et Makefile compris), le dépôt de la formation dans votre home WSL, et les bases de la programmation orientée objet en Python (B0).

La formation B3 est adaptée du tutoriel [Week 1-2: Introduction to ROS2](https://github.com/MOGI-ROS/Week-1-2-Introduction-to-ROS2) du groupe MOGI-ROS (Université BME, Budapest). Le tutoriel d'origine est écrit pour ROS 2 Jazzy installé directement sur Ubuntu 24.04 ; ici, tout est ramené à ROS 2 Humble, au conteneur de B2 et aux drones.

Adapter le chemin à l'endroit où vous avez cloné la formation. Le `make build` est obligatoire une première fois : l'image de B3 n'est pas celle de B2. ### 1.3 - Plusieurs terminaux

ROS 2 roule en général plusieurs nodes en même temps, chacune dans son terminal. Dans un nouveau terminal WSL (dans VS Code : Terminal → New Terminal, ou le bouton de division du terminal), toujours depuis le dossier de B3, refaire simplement :

```bash
make shell
```

`make shell` démarre le conteneur s'il ne roule pas encore, et sinon ouvre juste un shell de plus dedans. On peut en ouvrir autant qu'on veut, et les fermer (`exit`) dans n'importe quel ordre : rien ne s'arrête tant qu'on n'a pas tapé `make down`.

**En fin de séance** : `make down`, depuis n'importe quel terminal WSL du dossier de B3. Il arrête et supprime les conteneurs ; `example_ws` reste sur votre machine.

## 2 - Qu'est-ce que ROS 2

ROS (Robot Operating System) est un framework open source conçu pour faciliter le développement d'applications robotiques. Malgré son nom, ce n'est pas un système d'exploitation : c'est un ensemble d'outils, de librairies et de conventions qui simplifient la conception de comportements complexes, sur une grande variété de robots.

ROS a été lancé en 2007 par le laboratoire d'intelligence artificielle de Stanford, puis repris par Willow Garage. Le but : offrir une plateforme commune à la recherche et au développement en robotique, capable de supporter une large gamme d'applications, de favoriser la réutilisation du code et la collaboration au sein de la communauté.

Les raisons principales de son développement :

- **Standardisation** : une plateforme commune qui simplifie l'intégration de composants matériels et logiciels différents.
- **Modularité** : des composants logiciels modulaires et réutilisables (les nodes), faciles à partager et à adapter d'un robot à l'autre.
- **Collaboration** : une communauté de chercheurs et de développeurs qui a produit une immense collection d'outils et de librairies.

### 2.1 - De ROS 1 à ROS 2

ROS 2 a été développé pour corriger les limites de ROS 1 et répondre aux besoins de la robotique industrielle et commerciale. Le développement a commencé vers 2014, avec pour cibles la sécurité, la performance en temps réel et le support de plusieurs robots à la fois.

En pratique, la plus grande différence est dans le middleware, la couche qui transporte les messages. ROS 1 utilisait un système de transport maison et un maître central (`roscore`) par lequel tout passait, ce qui n'avait pas été pensé pour le temps réel ni pour les systèmes distribués. ROS 2 s'appuie sur DDS, un standard industriel, et n'a plus de maître : les nodes se découvrent entre elles sur le réseau. C'est ce que règle la ligne `RMW_IMPLEMENTATION=rmw_cyclonedds_cpp` du fichier Compose (Cyclone DDS est une des implémentations de DDS).

La dernière version de ROS 1, Noetic, visait Ubuntu 20.04 et a atteint sa fin de vie en mai 2025, en même temps qu'Ubuntu 20.04. L'équipe utilise **ROS 2 Humble**, la version associée à Ubuntu 22.04 (c'est pour ça que B2 insistait sur 22.04), supportée jusqu'en mai 2027, éventuellement l'équipe devra changer à **ROS 2 Jazzy et ubuntu 24.04**. 

### 2.2 - ROS 2 chez Zenith

Sur le drone, le logiciel de mission est un ensemble de nodes ROS 2 qui s'échangent des messages. mavros, lancé par `make mavros` en B2, est lui-même une node : il traduit les messages MAVLink du contrôleur de vol en topics ROS 2 (le `/mavros/state` lu en B2), et les commandes ROS 2 en MAVLink. Tout ce que B3 enseigne sert à parler à mavros et aux autres nodes du dépôt aeac-2026.

## 3 - Premiers nodes : talker et listener

ROS 2 vient avec quelques exemples tout faits (installés dans l'image par l'ajout B3 du Dockerfile). On s'en sert pour voir les concepts de base avant d'écrire du code.

La commande suivante démarre un publisher écrit en C++. Un **publisher** est une node qui envoie des messages d'un certain type sur un **topic** précis. Ici, le topic s'appelle `chatter` et le type est une chaîne de caractères.

Un topic est un canal de communication du modèle publish-subscribe : un message publié est reçu par tous les subscribers, contrairement aux files de messages (message queues), qui sont point à point et livrent chaque message à un seul consommateur. Les publishers diffusent des messages sur des topics, et les **subscribers** écoutent ces topics pour en recevoir une copie.

Le modèle publish-subscribe est asynchrone, de un à plusieurs ou de plusieurs à plusieurs : le publisher ne sait pas combien de subscribers l'écoutent (peut-être aucun). Il n'attend donc jamais de réponse ni de confirmation.

Dans le terminal de `make shell`, lancer le publisher C++ :

```bash
ros2 run demo_nodes_cpp talker
```

Résultat attendu :

```
[INFO] [1727116062.558281395] [talker]: Publishing: 'Hello World: 1'
[INFO] [1727116063.558177802] [talker]: Publishing: 'Hello World: 2'
[INFO] [1727116064.558010534] [talker]: Publishing: 'Hello World: 3'
[INFO] [1727116065.557939861] [talker]: Publishing: 'Hello World: 4'
[INFO] [1727116066.557849645] [talker]: Publishing: 'Hello World: 5'
```

Dans un deuxième terminal (`make shell`), démarrer un subscriber, écrit en Python cette fois, qui s'abonne au topic `chatter` et affiche ce que le publisher envoie :

    /listener/set_parameters_atomically: rcl_interfaces/srv/SetParametersAtomically

Pour l'instant, l'information la plus utile est de savoir à quels topics une node est abonnée (Subscribers) et sur lesquels elle publie (Publishers). Les paramètres et les services viennent en B3.2.

### 4.2 - Les topics

De la même façon, on liste les topics avec `ros2 topic list` :

```bash
ros2 topic list
```

```
/chatter
/parameter_events
/rosout
```

`/parameter_events` et `/rosout` sont créés par ROS 2 pour chaque node ; on les retrouvera partout.

Et on obtient les détails d'un topic avec `ros2 topic info /<topic>` :

```bash
ros2 topic info /chatter
```

```
Type: std_msgs/msg/String
Publisher count: 1
Subscription count: 1
```

Le terminal peut aussi s'abonner lui-même à un topic et afficher les messages qui passent, sans écrire une ligne de code. C'est la commande utilisée en B2 pour lire `/mavros/state` :

```bash
ros2 topic echo /chatter
```

```
data: 'Hello World: 212'
---
data: 'Hello World: 213'
---
```

`Ctrl+C` pour arrêter. `ros2 topic hz /chatter` mesure la fréquence de publication (une fois par seconde pour le talker), très utile pour vérifier qu'un capteur publie au rythme attendu.

### 4.3 - L'arbre des commandes

Toutes les commandes ROS 2 suivent la même forme : `ros2 <famille> <verbe> <arguments>`. Pas besoin de les apprendre par cœur, l'aide les liste à chaque niveau :

```bash
ros2 --help          # les familles : node, topic, service, param, pkg, run, launch...
ros2 topic --help    # les verbes de la famille topic : list, info, echo, hz, pub...
```

La touche `Tab` complète aussi les noms de commandes, de nodes et de topics.

Arrêter le talker et le listener avec `Ctrl+C`. On passe à nos propres nodes.

## 5 - Le workspace colcon

Pour créer, bâtir et rouler nos propres nodes, il faut des **packages**, et avant ça un **workspace** où les ranger. Deux termes à connaître :

- **ament** est le système de build des packages ROS 2. `ament_cmake` sert aux packages C/C++, basés sur CMake. `ament_python` sert à empaqueter et installer les nodes et les librairies Python.
- **colcon** (COmmand Line COLlectioN) est l'outil qui bâtit un workspace au complet. Il sait piloter plusieurs systèmes de build, dont ament, cmake et make.

Notre workspace sera donc un workspace colcon, qui utilise ament en arrière-plan pour bâtir chaque package. (Si vous avez fait du ROS 1 : colcon et ament remplacent catkin.)

### 5.1 - Créer le workspace

Le workspace existe déjà à moitié : c'est `/example_ws`, le volume monté par Compose. Il lui manque le dossier `src`, où vivront les sources de nos packages :

```bash
cd /example_ws
mkdir -p src
```

Au moment du build, colcon créera à côté de `src` trois dossiers : `build` (fichiers intermédiaires), `install` (ce qu'on roule réellement) et `log`. Comme `example_ws` est un volume, tout ça reste sur votre machine après `make down`.

### 5.2 - Créer un package Python

On entre dans `src` et on crée le premier package, en Python :

```bash
cd /example_ws/src
ros2 pkg create b3_python_nodes --build-type ament_python --dependencies rclpy std_msgs
```

À la création, il faut dire si le package est en C/C++ (`ament_cmake`) ou en Python (`ament_python`). **Sans précision, c'est toujours `ament_cmake`.** Le `--dependencies` inscrit tout de suite dans `package.xml` les packages dont le nôtre aura besoin : `rclpy` (l'API Python de ROS 2) et `std_msgs` (les types de messages standards).

> [!WARNING]
> **Piège** : le nom du package vient avant `--dependencies`. Placé après, il est pris pour une dépendance de plus, et la commande échoue avec `the following arguments are required: package_name`.

Nos scripts Python iront dans `b3_python_nodes/b3_python_nodes`, un dossier créé automatiquement avec le même nom que le package et qui contient déjà un fichier vide `__init__.py`. On y ajoute notre première node, `hello_world.py`, au choix :

- dans VS Code, dans `example_ws/src/b3_python_nodes/b3_python_nodes` (clic droit, New File) ;
- dans le terminal du conteneur : `touch /example_ws/src/b3_python_nodes/b3_python_nodes/hello_world.py`.

Les deux reviennent au même, c'est le volume : un fichier créé d'un côté apparaît de l'autre, et il vous appartient des deux côtés (l'utilisateur `dev` du conteneur porte votre UID, B2 section 2.5).

Le workspace doit maintenant ressembler à ceci (les autres fichiers ne comptent pas pour l'instant) :

```
example_ws/
└── src/
    └── b3_python_nodes/
        ├── b3_python_nodes/
        │   ├── __init__.py
        │   └── hello_world.py
        ├── package.xml
        ├── setup.cfg
        └── setup.py
```

Bonne pratique : remplir les champs `description`, `maintainer` (votre nom et votre courriel) et `license` dans `package.xml` et `setup.py`. Pour un package d'équipe, une licence permissive comme Apache 2.0 ou BSD est un bon choix.

### 5.3 - Une première node

Le hello world le plus simple possible, dans `hello_world.py` :

```python
#!/usr/bin/env python3

# Point d'entrée. args sert à passer des arguments à la fonction main
def main(args=None):
    print("Hello, world!")

# Vrai seulement si le script est exécuté directement (pas importé)
if __name__ == '__main__':
    main()
```

Même si c'est un script Python qui n'a pas besoin d'être compilé, il faut qu'ament l'empaquette, le copie et l'installe. **On ne roule jamais les scripts Python directement depuis le dossier source.**

Pour ça, on édite le `setup.py` généré à la création du package et on y ajoute un point d'entrée (entry point). Il indique le dossier, le nom du fichier (sans `.py`) et la fonction à appeler :

```python
    entry_points={
        'console_scripts': [
            'py_hello_world = b3_python_nodes.hello_world:main'
        ],
    },
```

À gauche du `=`, le nom de l'exécutable, celui qu'on donnera à `ros2 run`.

### 5.4 - Bâtir et rouler

**Le build se lance toujours depuis la racine du workspace**, jamais depuis `src` :

```bash
cd /example_ws
colcon build
```

```
Starting >>> b3_python_nodes
Finished <<< b3_python_nodes [1.21s]

Summary: 1 package finished [1.45s]
```

Un avertissement `SetuptoolsDeprecationWarning: setup.py install is deprecated` peut apparaître dans la sortie des packages Python : il est connu sous Humble et sans conséquence.

Après un build qui ajoute un nouveau package, il faut mettre à jour l'environnement du terminal pour que les outils ROS 2 le trouvent :

```bash
source install/setup.bash
```

Ce `source` ne vaut que pour le terminal où on le tape. Les terminaux ouverts **ensuite** par `make shell` le font tout seuls : c'est l'ajout B3 du Makefile qui source `install/setup.bash` s'il existe. À l'inverse, les terminaux ouverts **avant** ce premier build, ceux des sections 3 et 4, ne connaissent pas le workspace : y taper `source install/setup.bash`, ou les fermer et en rouvrir avec `make shell`.

On peut maintenant rouler notre première node :

```bash
ros2 run b3_python_nodes py_hello_world
```

```
Hello, world!
```

### 5.5 - Un hello world ROS 2

Cette première node roule, mais c'est un simple script Python qui n'utilise aucune fonction de ROS. On le transforme en vraie node ROS 2 avec `rclpy`, l'API Python de ROS 2, et ses fonctions de base : `init()`, `create_node()` et `shutdown()`. Pour explorer l'API plus en profondeur, la documentation de rclpy pour Humble est [ici](https://docs.ros.org/en/humble/p/rclpy/).

```python
#!/usr/bin/env python3
import rclpy # API Python de ROS 2

# Point d'entrée. args sert à passer des arguments à la fonction main
def main(args=None):
    rclpy.init(args=args)                          # Initialise l'API Python de ROS 2
    node = rclpy.create_node('python_hello_world') # Crée la node et lui donne un nom
    node.get_logger().info("Hello, ROS2!")         # Utilise le logger intégré de la node
    node.destroy_node()                            # Détruit la node
    rclpy.shutdown()                               # Ferme l'API Python de ROS 2

# Vrai seulement si le script est exécuté directement (pas importé)
if __name__ == '__main__':
    main()
```

Rien à changer dans `setup.py`, le point d'entrée est déjà là, mais il faut rebâtir le workspace. Après le build :

```bash
colcon build
ros2 run b3_python_nodes py_hello_world
```

```
[INFO] [1727525512.304731280] [python_hello_world]: Hello, ROS2!
```

Le logger de ROS 2 ajoute le niveau (`INFO`), l'heure et le nom de la node à chaque ligne. C'est le format de tous les messages vus depuis le début, mavros compris.

## 6 - Un publisher en Python

Premier vrai publisher, dans un nouveau fichier `publisher.py` du dossier `b3_python_nodes/b3_python_nodes`. On y ajoute les fonctions de l'API liées à la publication : `create_publisher()` et `publish()`.

```python
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node     # Classe Node de ROS 2, parent de notre propre node
from std_msgs.msg import String # Type du message : une chaîne de caractères

class MyPublisherNode(Node):
    def __init__(self):
        super().__init__("python_publisher")                         # Nom de la node
        self.publisher_ = self.create_publisher(String, 'topic', 10) # Type, nom du topic, taille de la file
        self.timer = self.create_timer(0.5, self.timer_callback)     # Période en secondes, pas une fréquence!
        self.i = 0
        self.msg = String()
        self.get_logger().info("Publisher démarré.")

    def timer_callback(self):                                        # Appelée à chaque période du timer
        self.msg.data = f"Hello, world: {self.i}"
        self.i += 1
        self.get_logger().info(f'Publication : "{self.msg.data}"')
        self.publisher_.publish(self.msg)

def main(args=None):
    rclpy.init(args=args)
    node = MyPublisherNode() # node est maintenant une classe maison basée sur Node
    rclpy.spin(node)         # Garde la node en vie jusqu'au Ctrl+C
    node.destroy_node()
    rclpy.shutdown()

if __name__ == "__main__":
    main()
```

Quelques points sur ce code :

- **La node est une classe** qui hérite de `Node`. C'est la forme de presque tous les nodes de l'équipe.
- **Le `10` de `create_publisher`** est la taille de la file d'attente : si les messages partent plus vite qu'ils ne sont livrés, ROS 2 en garde au plus dix avant de jeter les plus vieux.
- **`rclpy.spin(node)`** donne la main à ROS 2, qui appelle `timer_callback` toutes les 0,5 seconde jusqu'au `Ctrl+C`.

On enregistre la nouvelle node comme point d'entrée dans `setup.py` :

```python
    entry_points={
        'console_scripts': [
            'py_hello_world = b3_python_nodes.hello_world:main',
            'py_publisher = b3_python_nodes.publisher:main'
        ],
    },
```

Rebâtir le workspace, puis rouler la nouvelle node :

```bash
colcon build
ros2 run b3_python_nodes py_publisher
```

```
[INFO] [1727526317.469012345] [python_publisher]: Publisher démarré.
[INFO] [1727526317.970055907] [python_publisher]: Publication : "Hello, world: 0"
[INFO] [1727526318.471461827] [python_publisher]: Publication : "Hello, world: 1"
[INFO] [1727526318.973896872] [python_publisher]: Publication : "Hello, world: 2"
[INFO] [1727526319.477439178] [python_publisher]: Publication : "Hello, world: 3"
```

## 7 - Un publisher en C++

En ROS 1, mélanger des nodes de langages différents dans un même package était simple. En ROS 2, c'est possible mais demande de retoucher les métadonnées du package à la main, parce que le type de build est fixé d'avance pour ament. Pour rester simple, on crée un deuxième package (l'article [Create a ROS2 package for both Python and Cpp nodes](https://roboticsbackend.com/ros2-package-for-both-python-and-cpp-nodes/) montre comment mélanger les deux au besoin) :

```bash
cd /example_ws/src
ros2 pkg create b3_cpp_nodes --build-type ament_cmake --dependencies rclcpp std_msgs
```

Créer `publisher.cpp` dans le dossier `b3_cpp_nodes/src`. Il reprend la structure orientée objet du publisher Python, timer compris. L'API C++ de ROS 2, `rclcpp`, offre pratiquement les mêmes fonctions que `rclpy`.

```cpp
#include "rclcpp/rclcpp.hpp"
#include "std_msgs/msg/string.hpp"

class MyPublisherNode : public rclcpp::Node
{
public:
    MyPublisherNode() : Node("cpp_publisher"), count_(0)
    {
        publisher_ = this->create_publisher<std_msgs::msg::String>("topic", 10);
        timer_     = this->create_wall_timer(std::chrono::milliseconds(500),
                                             std::bind(&MyPublisherNode::publishString, this));
        RCLCPP_INFO(this->get_logger(), "Publisher C++ démarré.");
    }

private:
    void publishString()
    {
        auto msg = std_msgs::msg::String();
        msg.data = "Hello, world: " + std::to_string(this->count_++);
        RCLCPP_INFO(this->get_logger(), "Publication : '%s'", msg.data.c_str());
        publisher_->publish(msg);
    }

    size_t count_;
    rclcpp::Publisher<std_msgs::msg::String>::SharedPtr publisher_;
    rclcpp::TimerBase::SharedPtr timer_;
};

int main(int argc, char **argv)
{
    rclcpp::init(argc, argv);
    rclcpp::spin(std::make_shared<MyPublisherNode>());
    rclcpp::shutdown();
    return 0;
}
```

Pour déclarer la node dans les métadonnées du package, on édite `b3_cpp_nodes/CMakeLists.txt`. Grâce au `--dependencies`, les deux `find_package` sont déjà là :

```cmake
find_package(rclcpp REQUIRED)
find_package(std_msgs REQUIRED)
```

Il reste à ajouter, **après les `find_package` et avant la ligne `ament_package()`** (qui doit rester la dernière du fichier) :

```cmake
add_executable(publisher_cpp src/publisher.cpp)
ament_target_dependencies(publisher_cpp rclcpp std_msgs)

install(TARGETS
  publisher_cpp
  DESTINATION lib/${PROJECT_NAME})
```

`add_executable` compile `publisher.cpp` en un exécutable nommé `publisher_cpp`, `ament_target_dependencies` le lie aux librairies de ROS 2, et `install` le copie là où `ros2 run` le cherche.

Bâtir, puis sourcer (c'est un nouveau package), puis rouler :

```bash
cd /example_ws
colcon build
source install/setup.bash
ros2 run b3_cpp_nodes publisher_cpp
```

## 8 - Un subscriber en Python

Nouveau fichier `subscriber.py` dans le package Python (`b3_python_nodes/b3_python_nodes`). On ajoute la fonction de l'API liée aux abonnements : `create_subscription()`.

```python
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class MySubscriberNode(Node):
    def __init__(self):
        super().__init__("python_subscriber")
        # Type, nom du topic, fonction appelée à chaque message, taille de la file
        self.subscriber_ = self.create_subscription(String, 'topic', self.subscriber_callback, 10)
        self.get_logger().info("Subscriber démarré.")

    def subscriber_callback(self, msg):                 # Reçoit le message en paramètre
        self.get_logger().info(f"Reçu : {msg.data}")

def main(args=None):
    rclpy.init(args=args)
    node = MySubscriberNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == "__main__":
    main()
```

Ajouter la node à `setup.py` comme nouveau point d'entrée :

```python
    entry_points={
        'console_scripts': [
            'py_hello_world = b3_python_nodes.hello_world:main',
            'py_publisher = b3_python_nodes.publisher:main',
            'py_subscriber = b3_python_nodes.subscriber:main'
        ],
    },
```

Rebâtir le workspace, puis lancer le publisher Python dans un terminal et le subscriber dans un autre. Le deuxième terminal doit connaître le workspace : un terminal ouvert après le premier build (nouveau `make shell`), ou un ancien dans lequel on a tapé `source install/setup.bash`.

```bash
colcon build
ros2 run b3_python_nodes py_publisher      # terminal 1
```

```bash
ros2 run b3_python_nodes py_subscriber     # terminal 2
```

## 9 - colcon au quotidien

Quelques réflexes pour ne pas perdre de temps avec le workspace.

**Toujours bâtir depuis `/example_ws`.** Un `colcon build` lancé depuis `src` ou depuis un package crée des dossiers `build`, `install` et `log` au mauvais endroit. Si ça arrive, les effacer et relancer depuis la racine.

**Bâtir un seul package.** Quand le workspace grossit (celui d'aeac-2026 en compte une dizaine), on ne rebâtit que ce qu'on a touché :

```bash
colcon build --packages-select b3_python_nodes
```

**Éviter de rebâtir pour chaque modification Python.** Avec `--symlink-install`, colcon installe des liens vers les fichiers source au lieu de copies : une modification d'un `.py` existant est prise en compte au prochain `ros2 run`, sans build. Un nouveau fichier ou un nouveau point d'entrée demande quand même un build. Si on passe d'un mode à l'autre, nettoyer d'abord (voir plus bas), sinon colcon se plaint de fichiers qu'il ne peut pas remplacer.

```bash
colcon build --symlink-install
```

**Quand sourcer.** Après un build qui ajoute un package : `source install/setup.bash` dans chaque terminal déjà ouvert, ou ouvrir un nouveau terminal avec `make shell`. Une simple modification d'un package existant n'en demande pas.

**Effacer un package.** Supprimer son dossier dans `src` ne suffit pas : ses fichiers bâtis restent dans `build` et `install`, et `ros2 run` le trouve encore. Il faut aussi effacer ses dossiers de build :

```bash
cd /example_ws
rm -rf src/<package> build/<package> install/<package>
```

Puis ouvrir un nouveau terminal : l'ancien a encore le package dans son environnement et affiche des avertissements sur un chemin qui n'existe plus.

**Tout nettoyer.** Pour repartir d'un workspace propre (les sources de `src` ne sont pas touchées) :

```bash
rm -rf build install log    # dans le conteneur, depuis /example_ws
make clean                  # ou depuis WSL, dans le dossier de B3
```

Puis `colcon build`, et un nouveau terminal.

Les packages `b3_python_nodes` et `b3_cpp_nodes` servent encore en B3.2 : les garder.

## 10 - Aide-mémoire

### Commandes ROS 2

| Commande | Ce qu'elle fait |
|---|---|
| `ros2 node list`, `info` | Liste les nodes, ou donne les détails d'une node |
| `ros2 topic list`, `info`, `echo`, `hz` | Liste les topics, donne les détails d'un topic, affiche ses messages dans le terminal, mesure sa fréquence |
| `ros2 run <package> <exécutable>` | Démarre une node d'un package |
| `ros2 pkg create <nom>` | Crée un package ; `--build-type ament_cmake` ou `ament_python`, `--dependencies` pour les dépendances (après le nom) |
| `colcon build` | Bâtit le workspace, depuis sa racine ; `--packages-select`, `--symlink-install` |
| `source install/setup.bash` | Rend les packages du workspace visibles dans le terminal courant |
| `source /opt/ros/humble/setup.bash` | Rend ROS 2 lui-même utilisable (fait par le Makefile) |
| `ros2 launch <package> <fichier launch>` | Démarre un fichier launch d'un package (B3.2) |
| `ros2 param list`, `get`, `set` | Liste, lit ou modifie les paramètres d'une node (B3.2) |
| `ros2 service list`, `call` | Liste les services, ou en appelle un depuis le terminal (B3.2) |
| `ros2 interface package`, `show` | Liste les interfaces d'un package, ou affiche le contenu d'une interface (B3.2) |

### Cibles du Makefile de B3

| Commande | Ce qu'elle fait |
|---|---|
| `make build` | Bâtit l'image |
| `make shell` | Démarre le conteneur de travail s'il ne roule pas, et ouvre un shell dedans. Se répète dans autant de terminaux qu'on veut |
| `make mavros` | Démarre mavros dans son conteneur (B3.3, demande la simulation MP) |
| `make mavros-logs` | Suit les logs de mavros |
| `make listen-status` | Démarre mavros et affiche `/mavros/state` |
| `make clean` | Efface `build`, `install` et `log` du workspace |
| `make down` | Arrête et supprime les conteneurs |
