# Formation contrôle niveau 3 (B3.2) : launch, paramètres et services

## Objectifs de la formation

À la fin de cette partie, vous serez capable de :

- Démarrer plusieurs nodes d'un coup avec un fichier launch, et les renommer
- Déclarer un paramètre dans une node, le lire et le modifier en cours d'exécution, et le fixer depuis un fichier launch
- Expliquer la différence entre un topic et un service
- Définir un service maison dans un package d'interfaces
- Écrire un serveur et un client de service en Python, et appeler un service depuis le terminal

Prérequis : B3.1 terminé. Le package `b3_python_nodes` doit exister dans `example_ws/src` et se bâtir sans erreur.

Comme en B3.1, on travaille dans le conteneur : `make shell` dans chaque terminal (B3.1 section 1.3). Toutes les commandes se tapent dans un terminal du conteneur, et tous les `colcon build` se lancent depuis `/example_ws`.

## 1 - Les fichiers launch

Jusqu'ici, il fallait autant de terminaux que de nodes. Avec un publisher et un subscriber, ça passe, mais dans un vrai projet robotique, on roule couramment des dizaines de nodes, parfois des centaines. ROS 2 offre donc un moyen de démarrer plusieurs nodes ensemble, et même de renommer leurs topics ou de changer leurs paramètres sans toucher à leur code : les fichiers launch.

Vous en utilisez un depuis B2 sans le savoir : le Makefile démarre mavros avec `ros2 launch mavros apm.launch`.

### 1.1 - Un package pour les fichiers launch

La bonne pratique est de donner aux fichiers launch un package à eux. C'est ce que fait aeac-2026 avec son package `bringup`, qui contient un fichier launch par mission (`ros2 launch bringup water_mission.launch.py`, par exemple).

On crée un package `ament_python`, comme `b3_python_nodes`, mais il ne contiendra aucun code :

```bash
cd /example_ws/src
ros2 pkg create b3_bringup --build-type ament_python
```

Dans ce nouveau package, on crée un dossier `launch` :

```bash
cd b3_bringup
mkdir launch
```

Pour que colcon installe le contenu de `launch` au build, on l'ajoute aux `data_files` de `b3_bringup/setup.py`. Les deux premières entrées existent déjà ; on ajoute les deux imports en tête de fichier et la troisième entrée :

```python
import os                      # ajouté
from glob import glob          # ajouté
from setuptools import setup

package_name = 'b3_bringup'

setup(
    name=package_name,
    version='0.0.0',
    packages=[package_name],
    data_files=[
        ('share/ament_index/resource_index/packages',
            ['resource/' + package_name]),
        ('share/' + package_name, ['package.xml']),
        # Ajouté : tous les fichiers *.launch.py du dossier launch, installés
        # dans share/b3_bringup/launch, là où ros2 launch les cherche
        (os.path.join('share', package_name, 'launch'),
         glob(os.path.join('launch', '*.launch.py'))),
    ],
    # ... le reste du fichier ne change pas
)
```

C'est mot pour mot le `setup.py` du package `bringup` d'aeac-2026.

### 1.2 - Un premier fichier launch

Dans le dossier `launch`, créer le fichier `publisher_subscriber.launch.py`.

En ROS 2, les fichiers launch sont des scripts Python déclaratifs (avec une touche impérative), et non les fichiers XML de ROS 1. ROS 2 accepte aussi des fichiers launch en XML, et certains packages s'en servent (le `apm.launch` de mavros en est un), mais la documentation du format XML est mince et la communauté a surtout adopté les fichiers Python.

On commence par un modèle réutilisable qui ne démarre qu'une seule node, le publisher de B3.1. Pour chaque node ajoutée à un fichier launch, on donne le package, l'exécutable et un nom choisi librement :

```python
#!/usr/bin/env python3
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    ld = LaunchDescription()

    publisher_node = Node(
        package="b3_python_nodes",
        executable="py_publisher",
        name="my_publisher"
    )

    ld.add_action(publisher_node)
    return ld
```

Bâtir, puis sourcer, puisqu'on a ajouté un package :

```bash
cd /example_ws
colcon build
source install/setup.bash
```

On lance le fichier avec `ros2 launch` :

```bash
ros2 launch b3_bringup publisher_subscriber.launch.py
```

### 1.3 - Ajouter le subscriber

Chaque node ajoutée au fichier launch doit aussi être enregistrée avec `ld.add_action()` :

```python
#!/usr/bin/env python3
from launch import LaunchDescription
from launch_ros.actions import Node

def generate_launch_description():
    ld = LaunchDescription()

    publisher_node = Node(
        package="b3_python_nodes",
        executable="py_publisher",
        name="my_publisher",
    )

    subscriber_node = Node(
        package="b3_python_nodes",
        executable="py_subscriber",
        name="my_subscriber",
    )

    ld.add_action(publisher_node)
    ld.add_action(subscriber_node)
    return ld
```

## 2 - Les paramètres

ROS 2 donne accès aux paramètres des nodes : on peut les lister, lire leur valeur et la modifier avec `ros2 param list`, `ros2 param get` et `ros2 param set`.

### 2.1 - Les paramètres d'une node existante

Démarrer le publisher Python de B3.1 :

```bash
ros2 run b3_python_nodes py_publisher
```

Et dans un autre terminal :

```bash
ros2 param list /python_publisher
```

```
  use_sim_time
```

La liste n'est pas vide alors qu'on n'a rien déclaré : `use_sim_time` est un paramètre que ROS 2 crée pour chaque node. Il mérite d'être retenu : il dit à la node d'utiliser l'horloge du simulateur plutôt que celle de la machine. La cible `mavros-gazebo` d'aeac-2026 le met à `true`.

### 2.2 - Une node avec son propre paramètre

On écrit un autre publisher Python, cette fois avec un paramètre déclaré par l'API. Nouveau fichier `publisher_with_param.py` dans `b3_python_nodes/b3_python_nodes`, sur le modèle de `publisher.py` :

```python
#!/usr/bin/env python3
import rclpy
from rclpy.node import Node
from std_msgs.msg import String

class MyPublisherNode(Node):
    def __init__(self):
        super().__init__("python_publisher_with_param")
        self.declare_parameter("published_text", "Zenith")        # Déclare le paramètre avec une valeur par défaut
        self.text_ = self.get_parameter("published_text").value   # Copie sa valeur dans la variable text_

        self.publisher_ = self.create_publisher(String, 'topic', 10)
        self.timer = self.create_timer(0.5, self.timer_callback)
        self.i = 0
        self.msg = String()
        self.get_logger().info("Publisher avec paramètre démarré.")

    def timer_callback(self):
        self.msg.data = f"{self.text_}: {self.i}"                 # Utilise text_ dans le message
        self.i += 1
        self.get_logger().info(f'Publication : "{self.msg.data}"')
        self.publisher_.publish(self.msg)

def main(args=None):
    rclpy.init(args=args)
    node = MyPublisherNode()
    rclpy.spin(node)
    node.destroy_node()
    rclpy.shutdown()

if __name__ == "__main__":
    main()
```

L'enregistrer dans `setup.py` :

```python
    entry_points={
        'console_scripts': [
            'py_hello_world = b3_python_nodes.hello_world:main',
            'py_publisher = b3_python_nodes.publisher:main',
            'py_subscriber = b3_python_nodes.subscriber:main',
            'py_publisher_with_param = b3_python_nodes.publisher_with_param:main'
        ],
    },
```

Rebâtir et rouler :

```bash
colcon build
ros2 run b3_python_nodes py_publisher_with_param
```

Puis, dans un autre terminal, lister ses paramètres :

```bash
ros2 param list /python_publisher_with_param
```

```
  published_text
  use_sim_time
```

Le paramètre `published_text` est maintenant visible pour ROS 2.

La gestion des paramètres est une grande différence entre ROS 1 et ROS 2. En ROS 1, c'était une fonction centralisée du maître (`roscore`) : chaque node déclarait ses paramètres au serveur de paramètres global, et on ne pouvait les modifier qu'en passant par lui. En ROS 2, il n'y a plus de serveur de paramètres : chaque node gère les siens.

### 2.3 - Lire et modifier un paramètre

Lire la valeur avec `ros2 param get` :

```bash
ros2 param get /python_publisher_with_param published_text
```

```
String value is: Zenith
```

Maintenant, essayer de la changer de `Zenith` à `Polytechnique` :

```bash
ros2 param set /python_publisher_with_param published_text Polytechnique
```

```
Set parameter successful
```

Le paramètre a bien changé (`ros2 param get` le confirme), mais le texte publié, lui, ne bouge pas. C'est parce que `self.text_` est rempli une seule fois, dans le constructeur : la node ne relit jamais le paramètre après. Ce n'est pas forcément une erreur. Pour un paramètre qu'on ne veut fixer qu'au démarrage, c'est le bon comportement. Le nom d'un topic ou la fréquence d'un timer, par exemple, sont souvent des paramètres de démarrage.

Ici, on veut pouvoir changer le texte en cours de route. On déplace donc la lecture du paramètre dans `timer_callback()`, pour qu'elle se fasse à chaque période :

```python
    def timer_callback(self):
        self.text_ = self.get_parameter("published_text").value  # Relu à chaque période
        self.msg.data = f"{self.text_}: {self.i}"
        self.i += 1
        self.get_logger().info(f'Publication : "{self.msg.data}"')
        self.publisher_.publish(self.msg)
```

Rebâtir le workspace, relancer la node et modifier le paramètre comme avant. Cette fois, le texte publié change en cours d'exécution :


## 3 - Les services

### 3.1 - Topic ou service

Rappel du modèle publish-subscribe, tel que défini en B3.1 : asynchrone, de un à plusieurs ou de plusieurs à plusieurs, le publisher ne sait pas combien de subscribers l'écoutent (peut-être aucun) et n'attend donc jamais de réponse.

Les services sont différents sur plusieurs points, et servent à autre chose :

- Un service est une communication synchrone : un **client** envoie une requête (request) au **serveur**, qui la traite et renvoie une réponse (response).
- C'est une interaction strictement un à un.
- L'échange ne se termine qu'une fois la requête traitée et la réponse renvoyée.
- Les services conviennent aux opérations ponctuelles de type question-réponse.

Côté drone : un flux continu comme la position ou l'état passe par des topics (`/mavros/state`), alors qu'une action ponctuelle dont on veut savoir si elle a réussi, comme armer les moteurs ou changer de mode de vol, passe par des services (`/mavros/cmd/arming`, `/mavros/set_mode`).

### 3.2 - Définir un service

Avant d'écrire un serveur ou un client, il faut définir le service : le contenu de la requête et celui de la réponse. En ROS 2, on place d'habitude les messages, services et actions maison dans un package à part. C'est le rôle de `custom_interfaces` dans aeac-2026. On crée ici `b3_interfaces` :

```bash
cd /example_ws/src
ros2 pkg create b3_interfaces
```

Le package doit être de type `ament_cmake` : soit on le précise avec `--build-type ament_cmake`, soit on se fie au défaut.

On crée un dossier `srv`, où vivra le service, et on efface les dossiers `include` et `src` :

```bash
cd b3_interfaces
rm -rf include/ src/
mkdir srv
```

Dans `srv`, créer le fichier `CustomCalc.srv`, avec cette structure requête-réponse. La partie au-dessus des `---` est la requête, celle en dessous est la réponse :

```
int64 a
int64 b
---
int64 result
```

Dans `b3_interfaces/CMakeLists.txt`, ajouter ces lignes **avant `ament_package()`**. Elles génèrent le code Python et C++ du service à partir du fichier `.srv` :

```cmake
find_package(rosidl_default_generators REQUIRED)

rosidl_generate_interfaces(${PROJECT_NAME}
  "srv/CustomCalc.srv"
)
```

Et dans `b3_interfaces/package.xml`, ajouter ces lignes à l'intérieur de la balise `<package>`, par exemple juste sous `<buildtool_depend>ament_cmake</buildtool_depend>` :

```xml
  <buildtool_depend>rosidl_default_generators</buildtool_depend>
  <exec_depend>rosidl_default_runtime</exec_depend>
  <member_of_group>rosidl_interface_packages</member_of_group>
```

Bâtir le workspace, puis sourcer, puisqu'on a ajouté un package :

```bash
cd /example_ws
colcon build
source install/setup.bash
```

On vérifie que le service a bien été créé avec `ros2 interface package` :

```bash
ros2 interface package b3_interfaces
```

```
b3_interfaces/srv/CustomCalc
```

Et on regarde son contenu avec `ros2 interface show` :

```bash
ros2 interface show b3_interfaces/srv/CustomCalc
```

```
int64 a
int64 b
---
int64 result
```

La même commande marche sur les services de mavros : `ros2 interface show mavros_msgs/srv/CommandBool` affiche ce qu'il faut envoyer pour armer le drone.

### 3.3 - Le serveur

Nouvelle node Python, `service_server.py`, dans `b3_python_nodes/b3_python_nodes` :

```python
#!/usr/bin/env python3
from b3_interfaces.srv import CustomCalc # Notre service maison

import rclpy
from rclpy.node import Node

class MyService(Node):
    def __init__(self):
        super().__init__('my_service')
        # Crée un serveur de service : type, nom du service, fonction appelée à chaque requête
        self.srv = self.create_service(CustomCalc, 'custom_calc', self.custom_calc_callback)

    # La fonction d'un service reçoit la requête et la réponse à remplir
    def custom_calc_callback(self, request, response):
        response.result = request.a + request.b
        self.get_logger().info('Requête reçue\na: %d b: %d' % (request.a, request.b))
        return response

def main():
    rclpy.init()
    my_service_server = MyService()
    rclpy.spin(my_service_server)
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

Ajouter le point d'entrée dans `setup.py` :

```python
            'py_service_server = b3_python_nodes.service_server:main'
```

(Sans oublier la virgule à la fin de la ligne précédente.)

Il faut aussi éditer `b3_python_nodes/package.xml`, parce que notre package dépend maintenant du package d'interfaces. Ajouter, à côté des `<depend>` de `rclpy` et `std_msgs` :

```xml
  <depend>b3_interfaces</depend>
```

Grâce à cette ligne, colcon sait qu'il doit bâtir `b3_interfaces` avant `b3_python_nodes`.

Rebâtir le workspace et rouler la nouvelle node :

```bash
colcon build
ros2 run b3_python_nodes py_service_server
```

Pour écrire un serveur de service en C++, voir le tutoriel officiel [Writing a simple service and client (C++)](https://docs.ros.org/en/humble/Tutorials/Beginner-Client-Libraries/Writing-A-Simple-Cpp-Service-And-Client.html).

### 3.4 - Le client

Nouvelle node Python, `service_client.py`, dans `b3_python_nodes/b3_python_nodes` :

```python
#!/usr/bin/env python3
import sys

from b3_interfaces.srv import CustomCalc # Notre service maison

import rclpy
from rclpy.node import Node

class MyServiceClientAsync(Node):
    def __init__(self):
        super().__init__('my_service_client_async')
        # Crée un client de service
        self.cli = self.create_client(CustomCalc, 'custom_calc')
        # Attend que le serveur soit en ligne
        while not self.cli.wait_for_service(timeout_sec=1.0):
            self.get_logger().info('Service non disponible, nouvelle tentative...')
        # Prépare la requête
        self.req = CustomCalc.Request()

    def send_request(self, a, b):
        self.req.a = a
        self.req.b = b
        # Envoie la requête sans bloquer. Le résultat arrivera dans le "future"
        return self.cli.call_async(self.req)

def main():
    rclpy.init()
    my_service_client = MyServiceClientAsync()
    future = my_service_client.send_request(int(sys.argv[1]), int(sys.argv[2]))
    # Fait tourner la node seulement jusqu'à l'arrivée de la réponse
    rclpy.spin_until_future_complete(my_service_client, future)
    response = future.result()
    my_service_client.get_logger().info(
        'Résultat de custom_calc : %d + %d = %d' %
        (int(sys.argv[1]), int(sys.argv[2]), response.result))

    my_service_client.destroy_node()
    rclpy.shutdown()

if __name__ == '__main__':
    main()
```

`call_async` envoie la requête et rend la main tout de suite, avec un objet `future` qui contiendra la réponse quand elle arrivera. `spin_until_future_complete` fait tourner la node jusqu'à ce moment-là. Les deux nombres à additionner viennent de la ligne de commande (`sys.argv`).

Ajouter le point d'entrée dans `setup.py` :

```python
            'py_service_client = b3_python_nodes.service_client:main'
```

Rebâtir le workspace, démarrer d'abord le serveur :

```bash
colcon build
ros2 run b3_python_nodes py_service_server
```

Puis, dans un autre terminal, rouler le client avec deux nombres en arguments :

```bash
ros2 run b3_python_nodes py_service_client 3 4
```

```
[INFO] [1727626843.911245336] [my_service_client_async]: Résultat de custom_calc : 3 + 4 = 7
```

Le client se termine dès qu'il a sa réponse, alors que le serveur reste en ligne, prêt pour la requête suivante.

```
    ├── b3_python_nodes/
    │   ├── __init__.py
    │   ├── hello_world.py
    │   ├── publisher.py
    │   ├── subscriber.py
    │   ├── publisher_with_param.py
    │   ├── service_server.py
    │   └── service_client.py
    ├── package.xml
    ├── setup.cfg
    └── setup.py
```

(Les autres fichiers générés par `ros2 pkg create`, comme `resource/` et `test/`, ne sont pas listés.)

Et le `setup.py` de `b3_python_nodes` déclare six points d'entrée :

```python
    entry_points={
        'console_scripts': [
            'py_hello_world = b3_python_nodes.hello_world:main',
            'py_publisher = b3_python_nodes.publisher:main',
            'py_subscriber = b3_python_nodes.subscriber:main',
            'py_publisher_with_param = b3_python_nodes.publisher_with_param:main',
            'py_service_server = b3_python_nodes.service_server:main',
            'py_service_client = b3_python_nodes.service_client:main'
        ],
    },
```

C'est, en miniature, l'organisation d'aeac-2026 : les fichiers launch dans `bringup`, les définitions de messages et de services dans `custom_interfaces`, et le code des nodes dans leurs propres packages.

| Commande | Ce qu'elle fait |
|---|---|
| `ros2 launch <package> <fichier launch>` | Démarre tous les nodes d'un fichier launch |
| `ros2 param list`, `get`, `set` | Liste, lit ou modifie les paramètres d'une node |
| `ros2 service list`, `call` | Liste les services, ou en appelle un depuis le terminal |
| `ros2 interface package`, `show` | Liste les interfaces d'un package, ou affiche le contenu d'une interface |
